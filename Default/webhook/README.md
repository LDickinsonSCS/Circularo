# CRO webhook receiver – deployment (IIS on the TTA server, SCSDEMO)

Circularo posts document events to `https://portal.sudocodesolutions.com/cro-webhook/receive.ashx`.
The handler checks the HMAC signature, stores the event in `cro.webhook_event`, and returns 200. The `CRO Sync` process does all processing.

## Files
- `receive.ashx` – the handler (compiled by IIS on first request; no build step).
- `web.config` – connection string to the `Circularo` database, request size limits.

## Steps
1. Create folder `C:\inetpub\cro-webhook` and copy both files into it.
2. In IIS Manager, under the site that serves **portal.sudocodesolutions.com**:
   - Right-click the site → **Add Application…**
   - Alias: `cro-webhook`, Physical path: `C:\inetpub\cro-webhook`.
   - Application pool: a **.NET CLR v4.0, Integrated** pool running as **SCSDEMO\scs-admin** (the account that already has access to the `Circularo` database). A dedicated pool `CroWebhook` is cleanest.
3. Check from a browser: `https://portal.sudocodesolutions.com/cro-webhook/receive.ashx` should return `{"service":"cro-webhook","ok":true}`.
4. Make sure the URL is reachable from the internet (Circularo's cloud posts to it over HTTPS).

## Security notes
- The HMAC secret is generated by `CRO API` (`webhook_setup`), stored DPAPI-encrypted (machine scope) in `cro.secret`, and registered with Circularo. It is never shown or stored in plain text. The handler decrypts it locally; it only works on this server.
- Invalid signatures are stored with `signature_valid = 0` for diagnosis and never acted on.
- Only `cro_api.webhook_receive` and `cro_api.secret_get` are called. For production, run the pool as a low-privilege account in role `cro_app`.
- To rotate the secret: run `webhook_setup` again (it registers a new webhook), then delete the old one with `webhook_delete`.
